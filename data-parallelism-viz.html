Data Parallelism: What's Actually Happening

An interactive walkthrough of why naive DP is wasteful, and how three optimizations fix it.

The setup: what data parallelism actually does

You have 4 GPUs. Each one holds a complete copy of the model (same parameters, same architecture). Every step, you split your batch into 4 microbatches — one per GPU. Each GPU does forward + backward on its own microbatch. Then you average the gradients across the 4 GPUs (an all-reduce), so all 4 GPUs apply the same update and stay in sync.

All 4 GPUs run forward + backward in parallel. The synchronization happens in the gradient averaging step.

Why an all-reduce? Because each GPU saw different data and produced different gradients. If you didn't average them, after one step the 4 GPUs would have drifted apart — they'd no longer be replicas of the same model. The all-reduce keeps them in lockstep: every GPU ends up with the same averaged gradient, applies the same optimizer step, and remains a true replica.

The GPU does all the backward work, then sits idle while the network shuffles 60ms worth of gradients around. The all-reduce isn't doing GPU work — the GPU is just waiting. That's wasted time.
The wasteful insight: While the all-reduce is running, the GPU is doing nothing. We've already finished backward by the time we start communicating. But we could have started talking much earlier — as soon as layer 4's gradient was ready, we could have started reducing it while still computing layer 3's backward.

Wait — why can't the GPU just start the next batch?

The natural first thought: "if the GPU is sitting idle during all-reduce, why doesn't it just start processing the next microbatch in the meantime?"

The answer is a hard mathematical constraint, not a software limitation. The next batch needs the updated weights. And the weights don't get updated until the optimizer step runs — which can't run until the all-reduce finishes.

The dependency chain is rigid:

backward  →  all-reduce  →  optimizer step  →  next forward

If you started the next forward pass during the all-reduce, you'd be running it on the same stale weights from the start of this step — not the updated ones. The math no longer matches synchronous SGD, which is the contract every modern frontier-scale recipe relies on. (There are async variants — asynchronous SGD, stale-gradient methods — but they have meaningfully worse optimization dynamics, and basically nobody trains frontier LLMs that way.)

So "start the next batch" is off the table. What's the actual opportunity?

The real insight

The all-reduce of layer N's gradient doesn't depend on the backward pass of layers N-1, N-2, ....

Why? Because backward flows from output to input. The backward pass for layer N-1 needs:

  • Layer N-1's stored activations (from forward — already in memory)
  • The gradient flowing back from layer N — which is just $\frac{\partial L}{\partial \text{input}(N)}$, computed locally on this GPU

It does not need the averaged gradient of layer N's parameters. Each GPU's local layer N gradient flows backward into layer N-1's local computation independently. The averaging across GPUs only matters later, when the optimizer step actually applies the update.

So the question shouldn't be "what other batch can the GPU work on?" It should be:

"What current-batch work is the GPU still going to do, that we could run in parallel with this all-reduce?"

And the answer is: the backward passes for the earlier layers. Layer 4's gradient is ready first. As soon as it's done, fire its all-reduce — meanwhile the GPU keeps grinding through backward for layer 3, then layer 2, then layer 1. The network handles layer 4's reduce while the SMs compute layer 3's gradient. Both pieces of hardware stay busy. Same step, no stale weights, no broken contracts.

Recast the intuition: "GPU idle during all-reduce" is the wrong framing. The right framing is "different parts of the gradient computation have different dependencies, so they can run on different hardware in parallel." Layer N's averaged gradient and layer N-1's local gradient are independent — one belongs on the network, the other on the GPU.

The only piece that can't overlap is the last layer's all-reduce (layer 1, the input layer). By the time layer 1's gradient is ready, backward is over — there's no more GPU work to hide it behind. That's the small "tail" you'll see at the end of the next timeline.

Optimization 1: Overlap all-reduce with backward pass

Backprop computes gradients from the last layer to the first. So layer 4's gradient is ready first, then layer 3's, then 2, then 1.

Insight: as soon as layer 4's gradient is computed, we don't need to wait for the other gradients to begin synchronizing it. We can start the all-reduce for layer 4 immediately, in parallel with the backward computation that's still running for layers 3, 2, 1.

In PyTorch this is implemented with a hook: a callback attached to each parameter that fires the moment its gradient is computed. The hook launches an async all-reduce for that parameter.

Each layer's all-reduce now starts the moment its backward finishes. By the time backward reaches layer 1, layers 4, 3, 2 have already been reduced. We only wait for the last all-reduce (layer 1's) before the optimizer step.

The bottom lane shows what the network is doing. Look at how it interleaves with the top lane — communication happens while the GPU is busy doing more backward work. Total step time drops from 270ms to 225ms.

The pattern: Computation and communication can run on different hardware (GPU compute units vs network interface). Whenever you can structure your work so they happen in parallel, you eliminate the cost of one of them. This pattern shows up everywhere in distributed training — FSDP, pipeline parallelism, tensor parallelism all use variants of it.

Optimization 2: Bucketing gradients

Now we have a new problem. The model isn't 4 layers — it's potentially thousands of parameters. If we launch one all-reduce per parameter, we're launching thousands of tiny network operations, each with its own overhead (setup latency, kernel launch, buffer allocation). That's like sending a thousand 1-byte packets instead of one kilobyte packet.

Solution: group multiple parameters into a bucket. When the bucket is full, launch a single all-reduce for the whole bucket.

Bucketing — fewer, larger all-reduces
Bucket size: 2 params per bucket
Each parameter has its gradient ready (top row, small green dots). With bucket size = 1, we get 8 separate all-reduces (each pays overhead). With bigger buckets, we get fewer but larger reduces. The total bytes transferred is the same, but the overhead drops dramatically.

In PyTorch DDP, the default bucket size is 25 MB. As gradients fill a bucket, it gets dispatched. This is the same idea as overlapping in Optimization 1 — but now the unit of overlap is a bucket, not an individual parameter.

Concrete numbers: For a 7B model with 200 parameter tensors, launching 200 all-reduces each with 30µs setup overhead = 6ms of pure overhead. With 5 buckets, overhead drops to 150µs. The actual data transferred is identical; only the number of "launches" changes.

Optimization 3: Gradient accumulation + no_sync

Sometimes you want a bigger effective batch than your GPUs can fit. The trick is gradient accumulation: do many forward+backward passes, accumulate the gradients into the same buffer, and only call the optimizer step after K passes.

But this interacts badly with naive DP. If you all-reduce after every backward pass during accumulation, you're paying the communication cost K times — when the only one that matters is the final one (the others are intermediate accumulation steps).

Gradients accumulate locally on each GPU without syncing. Only on the last microbatch — when we're about to step the optimizer — do we all-reduce. The communication cost drops by 4× for the same useful work.

Why is this safe? Because grad_GPU_0 + grad_GPU_1 + ... over microbatches gives the same final summed gradient whether you reduce after each microbatch or only at the end. Addition is commutative. As long as we do one all-reduce of the total accumulated gradients before the optimizer step, the result is mathematically identical.

PyTorch exposes this as model.no_sync():

for i, microbatch in enumerate(microbatches):
    is_last = (i == len(microbatches) - 1)
    context = nullcontext() if is_last else model.no_sync()
    with context:
        loss = model(microbatch)
        loss.backward()
optimizer.step()

Putting DP together

All three DP optimizations stack:

SetupWasted on communicationThroughput vs ideal
Naive DPAll of it (sequential)~60%
+ Overlap with backwardOnly the "tail" — last layer's reduce~85%
+ BucketingSame tail, but smaller overhead~92%
+ no_sync during accumulationOnly on the last accumulation step~97%

(Numbers are illustrative — actual throughput depends on the model, network, and accumulation depth. The point is the directional improvement.)

The unifying lesson: In distributed training, you almost never "do compute, then communicate, then compute again." That's always wasteful. The right model is "compute and communicate simultaneously, always, with the communication piggybacking on whatever compute is in flight." This same idea reappears in FSDP (prefetch next layer's params during current layer's compute), tensor parallelism (overlap all-reduce with subsequent layers), and pipeline parallelism (whole microbatches fly through the pipeline simultaneously).

Once you internalize overlap is everything, almost every distributed training trick starts looking like a variation on the same theme.

Part 2: ZeRO / FSDP — sharding the redundant stuff

DP solves throughput but wastes memory. ZeRO fixes the waste.

The problem DP doesn't solve

You've optimized DP all the way: backward overlap, bucketing, no_sync. Throughput is great. But look at your GPU memory.

With 8 GPUs running DDP on a 70B model, each GPU stores:

ComponentPer GPUAcross 8 GPUs
BF16 parameters140 GB1.12 TB (8× identical copies)
BF16 gradients140 GB1.12 TB (identical after all-reduce)
FP32 master weights + Adam $m$, $v$840 GB6.72 TB (identical)
Total1.12 TB / GPU9 TB total, but only 1.12 TB unique

You're storing 8 identical copies of everything. The cluster has 8× the memory of one GPU but holds only the same amount of unique state. That's pure waste.

The ZeRO insight: If 8 GPUs are storing the same 1.12 TB of state, each one should store 140 GB (1/8) and reconstruct the rest on demand via communication. Same unique state, 1/8 the per-GPU memory.

That's ZeRO. Three stages, each more aggressive than the last about what gets sharded.

The memory budget, restated

Following the ZeRO paper's notation: let $\Psi$ = parameter count. In BF16 training with Adam:

ComponentBytes per param
Parameters (BF16)$2\Psi$
Gradients (BF16)$2\Psi$
FP32 master weights + Adam $m$ + Adam $v$$4\Psi + 4\Psi + 4\Psi = 12\Psi$
Total (DDP)$\mathbf{16\Psi}$

ZeRO shards the $12\Psi$ optimizer-related state, then the $2\Psi$ gradients, then the $2\Psi$ parameters — in that order.

The critical correction: all-reduce vs reduce-scatter

Before going further: a single subtle change drives everything in ZeRO. The all-reduce in vanilla DDP becomes a reduce-scatter in ZeRO.

OpWhat every GPU has at the end
all-reduce(g)The full averaged gradient for every parameter
reduce-scatter(g)The averaged gradient for only its 1/N shard of parameters
all-gather(p)The full parameter tensor (assembled from everyone's shards)

The key identity:

all-reduce = reduce-scatter + all-gather

DDP does both halves at once (in the all-reduce). ZeRO splits them in time: reduce-scatter during backward (so each GPU only keeps its gradient shard), and all-gather after the optimizer step (so everyone has the updated parameters for the next forward).

The total bytes moved are the same — but now we have two opportunities to overlap communication with compute, and each GPU only ever has to store the slice it actively needs.

ZeRO-1: shard the optimizer state

The lightest stage. Each GPU still has the full BF16 parameters and full BF16 gradients (just like DDP), but only 1/N of the optimizer state (FP32 master weights + Adam moments).

ZeRO-1 — sharded optimizer state across 4 GPUs
Parameters (blue) and gradients (yellow) are duplicated — every GPU has the full set. Only the optimizer state (purple) is sharded. Each GPU holds its 1/4 slice of FP32 master weights + Adam m and v.

The training step in ZeRO-1

  1. Forward: each GPU has full BF16 params, runs forward on its microbatch. Same as DDP.
  2. Backward: each GPU computes the full $2\Psi$ BF16 gradients locally. Same as DDP.
  3. Reduce-scatter gradients: each GPU now has access to the averaged gradient for only its 1/N shard. But the full local gradient tensor is still in memory — ZeRO-1 doesn't bother dropping the unused portions.
  4. Optimizer step: each GPU updates only its 1/N slice of the FP32 master weights, using the 1/N gradient slice (the one it has Adam state for). The rest of the gradient is just sitting in memory, unused. Then casts its 1/N slice back to BF16.
  5. All-gather parameters: each GPU broadcasts its updated 1/N BF16 slice. After the gather, every GPU again has the full updated BF16 parameter tensor, ready for the next forward.
The subtle point that trips people up: In ZeRO-1, gradients are NOT sharded as persistent storage. The full $2\Psi$ gradient sits on every GPU. Reduce-scatter is still used (to deliver the right averaged slice for the optimizer step), but the unused 7/8 of the gradient is not freed. Each GPU's optimizer step only consumes its 1/N slice because that's the only part it has optimizer state for — the rest is just dead memory until the next backward overwrites it. This is exactly what ZeRO-2 fixes.

Memory math

Per-GPU memory: $2\Psi + 2\Psi + \frac{12\Psi}{N}$

For 70B on 8 GPUs: $140 + 140 + \frac{840}{8} = 385\,\text{GB}$ per GPU. Down from 1.12 TB. ~3× savings, no extra communication cost over DDP.

ZeRO-2: also shard the gradients

Recall the awkward thing about ZeRO-1: each GPU produced the full $2\Psi$ gradient during backward, reduce-scattered to learn its slice, then kept the unused 7/8 sitting in memory doing nothing. Wasteful.

ZeRO-2 fixes this with a small but powerful scheduling change: instead of one big reduce-scatter at the end of backward, do layer-by-layer reduce-scatters during backward — and free the local gradient memory for each layer as soon as its scatter completes.

The end result: each GPU never holds more than ~1/N of the gradient tensor at once. As backward progresses through layers, gradients are produced → scattered → dropped, layer by layer.

Same communication primitive in aggregate. Same total bytes moved. The change is purely when the scatter happens (layer-by-layer overlapped with backward, instead of one big one at the end) and whether you free the source memory after scattering (yes vs no).

ZeRO-2 — sharded optimizer state + gradients
Now both gradients (yellow) and optimizer state (purple) are sharded. Each GPU only holds 1/N of each. Parameters remain fully replicated.

It also stacks nicely with the DDP backward-overlap trick from earlier: the layer-by-layer reduce-scatters happen during the backward pass for earlier layers, hidden behind compute.

Memory math

Per-GPU memory: $2\Psi + \frac{2\Psi + 12\Psi}{N} = 2\Psi + \frac{14\Psi}{N}$

For 70B on 8 GPUs: $140 + \frac{14 \cdot 70}{8} = 140 + 122.5 = 262.5\,\text{GB}$ per GPU. ~4× savings vs DDP.

ZeRO-3: also shard the parameters (a.k.a. FSDP)

ZeRO-3 — and PyTorch's equivalent, FSDP — is the big leap. Now even the parameters themselves are sharded. Each GPU permanently stores only 1/N of the BF16 weights.

But the forward pass for a layer needs that layer's full weights. So before computing layer L's forward, every GPU all-gathers layer L's parameters from across the cluster. After the layer is done, drop the gathered weights. Same on backward — gather, compute, drop.

ZeRO-3 / FSDP — everything sharded
Parameters, gradients, and optimizer state are all sharded. Each GPU only persistently stores 1/N of each. Full layer weights exist transiently during each layer's forward/backward, then get dropped.

The training step in ZeRO-3

  1. Forward pass: for each layer, all-gather that layer's params → compute forward → drop the gathered params. Repeat for every layer.
  2. Backward pass: for each layer (output to input), all-gather params → compute backward → reduce-scatter the local gradient → drop both. Each GPU ends backward with only its 1/N gradient shard.
  3. Optimizer step: each GPU updates only its 1/N slice. No comm.
  4. No final all-gather needed — that's deferred until the next forward's per-layer all-gathers.

Memory math

Per-GPU memory: $\frac{2\Psi + 2\Psi + 12\Psi}{N} + \text{transient gather}$

For 70B on 8 GPUs: $\frac{16 \cdot 70}{8} = 140\,\text{GB}$ per GPU (plus a small transient buffer for whichever layer's params are currently gathered). ~8× savings vs DDP. Memory scales near-linearly with cluster size.

Why activations aren't in the list

A natural question: ZeRO shards parameters, gradients, optimizer state. Why not activations?

Because activations are already per-GPU. Each DP rank processes a different microbatch, so the activations it stores are computed from different data — they're not duplicates of each other, they're genuinely different tensors. Nothing to deduplicate.

Activations are tackled by a different family of tricks: activation checkpointing (drop and recompute on backward), sequence parallelism (covered in Part 3), and FlashAttention (never materialize the attention matrix). Each targets activations directly; ZeRO doesn't touch them.

The conceptual line: ZeRO/FSDP is the maximum amount of memory savings you can get while still keeping the premise "every GPU runs the same model on different data." Each GPU still computes the full forward pass on its own microbatch — it just has to gather some weights along the way. Once you start putting different parts of the model on different GPUs (tensor parallelism, pipeline parallelism), you've crossed into a different regime. That's the next post.

Putting all of Part 1 together

The four single-replica techniques (DDP optimizations + ZeRO) compose to give you frontier-scale-ready single-cluster training:

With ZeRO-3 + activation checkpointing, you can train a 70B model on a cluster of 8 H100s — modest by frontier standards but accessible to many research labs. Beyond that scale, you start running into FSDP's limits: very wide layers can't be gathered onto one GPU at all, and per-layer all-gathers become too chatty for inter-server networks.
